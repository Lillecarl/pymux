# Every difference between a picture of vttest with pymux in the chain
# and one without it. `tests/photograph_vttest.py` says what this is and
# how to write it.
#
# A line is a terminal, the screen by the menu path that reached it, and
# the verdict on it. The path is what `paths.txt` names, so a picture and
# a line here can always be lined up.
#
# A still screen is judged in pixels, and the verdict is how many differ.
# A blinking screen is judged twice: the same way, on a picture taken
# after its burst, and again on whether it blinks at all, under the same
# name with "(blink)" after it.
#
# Both are written down here, because a gate that is red for a reason
# everybody already knows is a gate everybody learns to ignore
# (Lillecarl/pymux#46). This check is not a gate yet either way: the
# chain is proven and the judging is not, and `photograph_vttest.py`
# says which part still flaps.
#
# Not every difference is a fault. A pane reads what a program asked for
# and writes the request again in a form the terminal of the user
# understands, so a pane can draw more than that terminal draws on its
# own, and it cannot do some of the things a terminal does to itself.
#
# A count is a number of pixels, so it belongs to the font, the size and
# the geometry that `take_a_picture.py` asks each terminal for. Change
# any of them and every count has to be recorded again.
#
# Only item 4 of vttest's main menu is recorded. Item 2 is measured and
# not written down, because two runs of it do not yet agree.

# Two things at once on these two screens, and only one of them is a
# fault.
#
# DECCOLM. vttest asks for 132 columns, and xterm answers by making its
# window wider: the bare picture is 132 cells across and 1280 pixels
# wide. A pane cannot do that. It has the cells the user gave it, and
# nothing in the protocol lets a program in a pane resize the window of
# the person running it, so the pymux picture stays 80 cells and 800
# pixels. That is not a fault and there is nothing to fix: a
# multiplexer exists because the terminal belongs to the user.
#
# `compare` measures the 800 pixels the two pictures share, so the width
# itself is not in the count. What is in it is the last cell of each
# double sized row, which holds the wrong letter: Lillecarl/pymux#116.
# A pane writes every cell of such a row, the cursor stops at the right
# margin, and the last character of the row overwrites the cell that is
# there. Both rows end in "line", so both show an "e".
#
# So these two counts fall when #116 is fixed, and they do not fall to
# zero. Record them again then.
xterm 4 Test of double-sized characters #3 1594
xterm 4 Test of double-sized characters #4 1594

# Blinking text that a pane loses. Bare xterm shows a blinking cell lit
# and leaves it lit, because the harness turns its blink timer off. A
# pane matches that for two frames, then paints the cell out and never
# paints it back.
#
# It shows twice on this screen: the burst sees one change where bare
# sees none, and the picture taken after the burst has the blinking text
# missing. Lillecarl/pymux#117.
xterm 4 Test of double-sized characters #5 5624
xterm 4 Test of double-sized characters #5 (blink) blinks-in-a-pane-only

# The cursor, two columns to the left of where it belongs. xterm puts it
# after "Push <RETURN>", which is column 52. ptterm's model says column
# 52 on both sides, so the pane holds the right answer and what pymux
# draws is two cells off. Lillecarl/pymux#115.
#
# The screen carries a blinking cell as well, and the pane loses that
# one too, which is #117 again. Only the cursor is in the count: the
# blinking cell here is the box border, and it is drawn in both
# pictures because the burst and the picture are not the same moment.
xterm 4 Test of double-sized characters #6 371
xterm 4 Test of double-sized characters #6 (blink) blinks-in-a-pane-only
