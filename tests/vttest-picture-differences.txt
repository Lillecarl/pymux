# Every difference between a picture of vttest with pymux in the chain
# and one without it. `tests/photograph_vttest.py` says what this is and
# how to write it.
#
# A line is a terminal, the screen by the menu path that reached it, and
# the verdict on it. The path is what `paths.txt` names, so a picture and
# a line here can always be lined up.
#
# A still screen is judged in pixels, and the verdict is how many differ.
# A blinking screen is judged twice: the same way, on a picture taken
# after its burst, and again on whether it blinks at all, under the same
# name with "(blink)" after it.
#
# Both are written down here, because a gate that is red for a reason
# everybody already knows is a gate everybody learns to ignore
# (Lillecarl/pyterm#48). The check is a gate, and it judges both ways:
# a count that goes down is a picture that changed too.
#
# Not every difference is a fault. A pane reads what a program asked for
# and writes the request again in a form the terminal of the user
# understands, so a pane can draw more than that terminal draws on its
# own, and it cannot do some of the things a terminal does to itself.
#
# A count is a number of pixels, so it belongs to the font, the size and
# the geometry that `take_picture.py` asks each terminal for. Change
# any of them and every count has to be recorded again.
#
# Item 4 of vttest's main menu is recorded, and item 9, which is what
# the check walks by default. Item 2 is measured and not written down,
# because two runs of it do not yet agree (Lillecarl/pyterm#119).

# Item 4 of vttest is entirely about the DEC line attributes. A pane
# holds them as kitty's text sizing, OSC 66 (Lillecarl/pyterm#892), and
# xterm speaks no OSC 66, so pymux draws each glyph of a double line at
# its ordinary size, one cell apart. xterm draws the same glyphs
# stretched. The text sits where xterm puts it; the glyphs differ, and
# that is the whole of every count here.
xterm 4 Test of double-sized characters #1 13516
xterm 4 Test of double-sized characters #2 16328

# The same, and DECCOLM as well. vttest asks for 132 columns, and
# xterm answers by making its window wider: the bare picture is 132
# cells across and 1280 pixels wide. A pane cannot do that. It has the
# cells the user gave it, and nothing in the protocol lets a program in
# a pane resize the window of the person running it, so the pymux
# picture stays 80 cells and 800 pixels. That is not a fault either: a
# multiplexer exists because the terminal belongs to the user.
#
# vttest still lays its text out for 132 columns, so what it writes past
# the 80th wraps onto the next row. Every judge of the panel does the
# same at 80 columns (Lillecarl/pyterm#374).
#
# `differences` crops the two pictures to the rectangle they share and
# measures that, so the 480 pixels of width that only one of them has
# are not in the count.
xterm 4 Test of double-sized characters #3 12336
xterm 4 Test of double-sized characters #4 15148

# The same again, on a screen that also blinks. xterm draws the blinking
# text bold for these pictures (`take_picture.py` says why), so both
# sides show it. Lillecarl/pyterm#599.

# "Exactly half of the box should remain." vttest draws a box and makes

# pane shows the same half, with its glyphs at their ordinary size.

# Item 9 is the screens that expose xterm's own bugs, one screen per
# bug, and the pane is not xterm: its emulator answers each question
# its own way, and the difference pictures are grey across most of the
# screen because the bug's behaviour is what the screen is of. The
# scroll region moves whole lines in the pane the way the emulator
# defines it. Every count is the emulator's answer or the glyphs of a
# double line, not a fault of pymux, and the pictures to read are the
# run's `differ/` directory. Lillecarl/pyterm#282.
