# Every difference between a picture of vttest with pymux in the chain
# and one without it. `tests/photograph_vttest.py` says what this is and
# how to write it.
#
# A line is a terminal, the screen by the menu path that reached it, and
# the verdict on it. The path is what `paths.txt` names, so a picture and
# a line here can always be lined up.
#
# A still screen is judged in pixels, and the verdict is how many differ.
# A blinking screen is judged twice: the same way, on a picture taken
# after its burst, and again on whether it blinks at all, under the same
# name with "(blink)" after it.
#
# Both are written down here, because a gate that is red for a reason
# everybody already knows is a gate everybody learns to ignore
# (Lillecarl/pymux#46). This check is not a gate yet either way: the
# chain is proven and the judging is not, and `photograph_vttest.py`
# says which part still flaps.
#
# Not every difference is a fault. A pane reads what a program asked for
# and writes the request again in a form the terminal of the user
# understands, so a pane can draw more than that terminal draws on its
# own, and it cannot do some of the things a terminal does to itself.
#
# A count is a number of pixels, so it belongs to the font, the size and
# the geometry that `take_a_picture.py` asks each terminal for. Change
# any of them and every count has to be recorded again.
#
# Item 4 of vttest's main menu is recorded, and item 9. Item 2 is
# measured and not written down, because two runs of it do not yet
# agree.

# Item 4 of vttest is entirely about the DEC line attributes, and a
# pane does not have them. "ESC # 3", "ESC # 4", "ESC # 5" and
# "ESC # 6" draw a line at twice the width or twice the height on a
# VT100. kitty, Ghostty and Alacritty implement none of them, esctest
# has no test for them, and no recorded program in this repository
# sends one. So a pane reads each of the four and draws the line the
# plain way. Lillecarl/pymux#141.
#
# Every count below is that, and it is the whole of every count. What
# a person sees: xterm draws each of these lines with glyphs twice as
# big, and the pane draws the same characters at their ordinary size.
# A double height line shows its text on both of its rows, because the
# program writes the text once for each half.
#
# These are the biggest counts in this file by far, and they are the
# least interesting. Six screens that are about one feature nobody
# implements say nothing else about the pane.
xterm 4 Test of double-sized characters #1 10841
xterm 4 Test of double-sized characters #2 12737

# The same, and DECCOLM as well. vttest asks for 132 columns, and
# xterm answers by making its window wider: the bare picture is 132
# cells across and 1280 pixels wide. A pane cannot do that. It has the
# cells the user gave it, and nothing in the protocol lets a program in
# a pane resize the window of the person running it, so the pymux
# picture stays 80 cells and 800 pixels. That is not a fault either: a
# multiplexer exists because the terminal belongs to the user.
#
# `compare` measures the 800 pixels the two pictures share, so the
# width itself is not in the count.
xterm 4 Test of double-sized characters #3 11514
xterm 4 Test of double-sized characters #4 13410
